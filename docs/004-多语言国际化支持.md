# 004 多语言国际化支持

> 需求编号：004-i8n（i8n 即 i18n，internationalization）
> 模块名称：多语言国际化支持
> 涉及工程：父工程、tpl-manage、tpl-manage-ui、tpl-app-api、tpl-app-web、tpl-app-android、tpl-app-harmony、tpl-app-mini
> 参考实现：RuoYi-Vue-Plus 6.0.0（后端）、RuoYi-Vue-Plus-UI v6.0.0（前端）
> 更新日期：2026-08-17

---

## 一、概述

本需求为「tpl-workspace」产品线引入**统一的多语言国际化（i18n）能力**：在父工程建立一个 i18n 语料总目录，作为全产品线所有子工程的多语言语料的**单一事实源（Single Source of Truth）**，并设计各子工程的落地方案与语料同步机制。

核心诉求拆解：

| 诉求 | 说明 |
|------|------|
| 语料总目录 | 父工程 `i18n/` 目录，存放全部多语言语料（存储方式本文档设计） |
| 管理端沿用 RVP 体系 | tpl-manage / tpl-manage-ui 沿用 RuoYi-Vue-Plus / UI 的 i18n 体系延续实现 |
| 用户端返回 key | tpl-app-api 返回到前端的 message 一律为 key，由前端拿 key 到语料中取文字 |
| 各端自实现 i18n | tpl-app-web / android / harmony / mini 按各自技术栈实现 i18n |
| 语料同步 | 语料在父工程与各子工程间如何同步，给出多个方案 |

本文档先完成**现状分析 + 方案设计**，落地实现（各子工程代码改动）在方案评审通过后另立任务执行。

## 二、RuoYi-Vue-Plus 后端 i18n 实现分析

RuoYi-Vue-Plus 6.0.0 的后端国际化是**两层机制**，二者互相独立：

### 2.1 第一层：消息 i18n（MessageSource）

这是「文案/异常/校验提示」的国际化，纯 Spring Boot 标准能力，RVP 未自定义 MessageSource Bean。

- **配置**：`ruoyi-admin/src/main/resources/application.yml` 中 `spring.messages.basename: i18n/messages`。**没有自定义的 `ReloadableResourceBundleMessageSource`**，MessageSource 由 Spring Boot 自动装配（`MessageSourceAutoConfiguration`，默认 `ResourceBundleMessageSource`，UTF-8）。
- **语料文件**：位于 `ruoyi-admin/src/main/resources/i18n/`，三个 bundle：
  - `messages.properties`（默认/兜底，中文）
  - `messages_zh_CN.properties`
  - `messages_en_US.properties`
- **取词入口**：`ruoyi-common-core/.../utils/MessageUtils.java`，静态方法 `MessageUtils.message(code, args...)` → `MessageSource.getMessage(code, args, LocaleContextHolder.getLocale())`，找不到时返回 code 本身。
- **校验消息**：`ruoyi-common-core/.../config/ValidatorConfig.java` 把 MessageSource 注入 Hibernate Validator（`setValidationMessageSource`），使 `@NotBlank(message = "{not.null}")` 之类的校验消息也走 i18n；`GlobalExceptionHandler`（ruoyi-common-web）对校验异常通过 `DefaultMessageSourceResolvable` 取已解析消息。

关键键名示例：`not.null`、`user.register.success`、`user.password.retry.limit.exceed`、`no.permission`、`rate.limiter.message`（支持 `{0}` 占位符）。

### 2.2 第二层：数据库字段翻译（@Translation）

这是「VO 字段值 → 语义化显示文本」的翻译（如 `deptId=1` → `研发部`、`sex=0` → `男`、`ossId` → `文件 URL`）。模块名是 **`ruoyi-common-translation`**（不是 `ruoyi-common-i18n`），并依赖 `ruoyi-common-json` 的 JSON 增强引擎。

- **注解**：`@Translation(type = ..., mapper = "源字段", other = "附加参数")`，标注在 VO 字段上。类型常量在 `TransConstant`：`USER_ID_TO_NAME`、`USER_ID_TO_NICKNAME`、`DEPT_ID_TO_NAME`、`DICT_TYPE_TO_LABEL`、`OSS_ID_TO_URL`。
- **处理链路**：`TranslationJsonFieldProcessor`（实现 `JsonFieldProcessor` 的 collect/prepare/process 三段式）→ 按 `(type, other)` 批量聚合待翻译键（避免 N+1）→ 调用对应 `TranslationInterface` 实现（`UserName/Nickname/DeptName/DictType/OssUrl TranslationImpl`）。
- **序列化集成**：`ruoyi-common-json` 的 `JsonValueEnhancer` 递归遍历出站 JSON 对象树，驱动所有 `JsonFieldProcessor`；`ResponseEnhancementAdvice`（`@RestControllerAdvice implements ResponseBodyAdvice`，注册于 `ResourcesConfig`）对 JSON 响应统一执行增强。
- **字典翻译**：`DictTypeTranslationImpl` 通过 `DictService.getDictLabel/getAllDictByDictType` 把字典值翻成 label；字典数据由 `SysDictTypeServiceImpl.selectDictDataByType` 经 Redis `@Cacheable(cacheNames = SYS_DICT)` 缓存。

> 注意：该引擎基于 `tools.jackson`（Jackson 3 / Spring Boot 4.x）。若目标工程是 Spring Boot 3.x + `com.fasterxml.jackson`，`JsonValueEnhancer` 内部需移植适配。

### 2.3 请求级 Locale 解析

- `ruoyi-common-web/.../core/I18nLocaleResolver.java`：实现 Spring `LocaleResolver`，读取请求头 **`content-language`**（不是 `Accept-Language`），兜底 `Locale.getDefault()`，`_` 归一化为 `-`。
- `ruoyi-common-web/.../config/I18nConfig.java`：`@AutoConfiguration`，注册上述 LocaleResolver Bean。
- **没有** `LocaleChangeInterceptor`；locale 由 Spring MVC 从 LocaleResolver 写入 `LocaleContextHolder`，`MessageUtils` 读取。

### 2.4 数据库 i18n 表结论

**RVP 6.0.0 不存在 `sys_i18n_dict` / `sys_i18n_dict_data` 表**。字典表是经典的 `sys_dict_type` / `sys_dict_data`，`dict_label` 为单一文本（非多语言）。字典 label 的多语言化是**前端**责任（plus-ui 用 i18n 翻），后端 `dict_type_to_label` 翻译只返回数据库原始 label。若本项目需要「字典值多语言」，属于需**自行扩展**的能力（见 §6.1）。

### 2.5 可复用点小结

| 复用点 | 位置 | 说明 |
|--------|------|------|
| MessageUtils | ruoyi-common-core | 取词门面，直接沿用 |
| I18nConfig + I18nLocaleResolver | ruoyi-common-web | `content-language` 头解析，沿用 |
| ValidatorConfig | ruoyi-common-core | 校验消息 i18n，沿用 |
| spring.messages.basename | 各启动模块 application.yml | 指定语料 basename |
| @Translation 引擎 | ruoyi-common-translation + ruoyi-common-json | 数据库字段翻译，可沿用（注意 Jackson 3 依赖） |

## 三、RuoYi-Vue-Plus-UI 前端 i18n 实现分析

RuoYi-Vue-Plus-UI 用 **vue-i18n（Composition 模式）** 实现前端国际化，架构精简（约 6 个核心文件）：

### 3.1 vue-i18n 装配

- `src/lang/index.ts`：`createI18n({ legacy: false, globalInjection: true, allowComposition: true, locale: getLanguage(), messages: { zh_CN, en_US } })`。导出 `getLanguage()`（读 `localStorage['language']`）与 `LanguageType`（`$t` 键类型来源）。
- `src/main.ts`：`app.use(i18n)` 注册一次。

### 3.2 语料文件组织

- `src/lang/zh_CN.ts` / `en_US.ts`：**扁平命名空间**的普通对象，按页面域分组：`route.*`、`login.*`、`register.*`、`navbar.*`，支持 `{placeholder}` 插值（如 `register.registerSuccess: '恭喜你，您的账号 {username} 注册成功！'`）。
- `src/types/module.d.ts`：用 `ObjKeysToUnion<LanguageType>` 递归映射类型给 `$t` 键提供 IDE 类型提示。
- `src/enums/LanguageEnum.ts`：`zh_CN` / `en_US` 枚举。

### 3.3 Locale 持久化与切换

- 持久化：`@vueuse/core` 的 `useStorage('language', 'zh_CN')`（localStorage），在 `lang/index.ts`（初始化）与 `store/modules/app.ts`（`language` 状态）各持有一份，共享同一 key。
- 切换：`src/components/LangSelect/index.vue`（el-dropdown），`handleLanguageChange` 同时写 vue-i18n 的 `locale` ref 和 app store；经 unplugin-vue-components 默认 `src/components` 扫描自动注册，出现在 Navbar、login、register 页。

### 3.4 Element Plus 语言包

- `store/modules/app.ts`：`import zhCN from 'element-plus/es/locale/lang/zh-cn'`、`import enUS from 'element-plus/es/locale/lang/en'`，`locale` computed 映射到 EP locale。
- `App.vue`：`<el-config-provider :locale="appStore.locale">` 包裹 `<router-view />`，切换语言时 EP 组件文案联动。

### 3.5 后端消息处理（关键差异）

**RVP-UI 不做后端消息的 key 翻译**。真实机制是：

- `src/utils/request.ts` 第 113 行：每个请求发送 `Content-Language: getLanguage()` 请求头。
- 后端 RVP 据此返回**已本地化的字符串**，拦截器直接 `ElMessage/ElNotification` 展示 `res.data.msg || errorCode[code] || errorCode['default']`。
- 唯一的前端翻译钩子 `src/utils/i18n.ts` 的 `translateRouteTitle(title)`（`i18n.global.te('route.' + title)` 守卫 + 兜底原值），**当前代码中无任何调用点**（死代码/遗留扩展点）；侧边栏、面包屑、标签页直接渲染 `meta.title`。

### 3.6 可复用点小结

| 复用点 | 位置 | 说明 |
|--------|------|------|
| createI18n 装配 | src/lang/index.ts | Composition 模式，直接沿用 |
| 语料文件结构 | src/lang/zh_CN.ts、en_US.ts | 扁平命名空间对象 |
| LangSelect 组件 | src/components/LangSelect | 语言切换 UI |
| EP locale 接线 | app store + App.vue el-config-provider | 组件库语言联动 |
| useStorage 持久化 | @vueuse/core | localStorage `language` |

**版本**：vue-i18n 11.4.8、element-plus 2.14.3、@vueuse/core 14.3.0、Vue 3.5.x。

## 四、各子工程 i18n 现状盘点

调研结论（`✅` 已有、`⚠️` 平台原生但未启用、`❌` 完全没有）：

| 子工程 | 技术栈 | 构建 | i18n 现状 |
|--------|--------|------|-----------|
| **tpl-manage** | Java 21 + Spring Boot 4.1.0（版本继承 RVP 6.0.0 BOM） | Maven 聚合（`<modules>` 引入 RVP + tpl-manage-admin） | ✅ 机制已继承（MessageUtils/I18nConfig/I18nLocaleResolver 在 ruoyi-common 依赖内）；⚠️ **但语料文件缺失**（见下） |
| **tpl-manage-ui** | Vue 3.5 + TS + Vite 8（Rolldown），pnpm | Vite，`@plus-ui` alias 继承 RVP-UI | ✅ 双层：本地 `src/lang/`（品牌包）+ 上游 `RuoYi-Vue-Plus-UI/src/lang/`（继承） |
| **tpl-app-api** | Spring Boot 4.1.0（独立 `spring-boot-starter-parent`）+ Sa-Token + MyBatis-Plus | Maven（mvnw） | ❌ 无任何 i18n；`R.java {code,msg,data}` 的 msg 为硬编码中文 |
| **tpl-app-web** | Vue 3.5 + TS + Vite 6 + Pinia，纯 CSS 无 UI 框架 | pnpm + Vite | ❌ 无 vue-i18n 依赖、无 src/lang、零 i18n 引用，文案硬编码 |
| **tpl-app-harmony** | ArkTS + ArkUI，Stage Model，API 5.1.1(19)~6.1.0(23) | Hvigor + ohpm，HAP + 3 HAR | ⚠️ 仅默认语言：`resources/base/element/string.json`（AppScope/products/default/common/features），无 `zh_CN/`、`en_US/` 资源目录 |
| **tpl-app-mini** | TypeScript + Skyline + glass-easel，微信原生 | 无构建工具链 | ❌ 无 i18n；`app.json` 无 locale 配置，tabBar/页面文案硬编码 WXML |

### 4.1 关键发现：tpl-manage 语料文件缺失

`tpl-manage-admin` 的 `application.yml` 已配置 `spring.messages.basename: i18n/messages`，但：

- RVP 的 `messages*.properties` 位于 `RuoYi-Vue-Plus/ruoyi-admin/src/main/resources/i18n/`；
- `tpl-manage-admin` 的依赖清单（`ruoyi-common-web`、`ruoyi-common-security`、`ruoyi-system`、`ruoyi-api` 等）**不含 `ruoyi-admin`**（那是 RVP 自己的启动模块，非库）；
- 故 RVP 的语料文件**大概率不在 tpl-manage-admin 运行时 classpath 上**，而 tpl-manage 自身也未提供语料文件。

结论：**tpl-manage 需要在 `tpl-manage-admin/src/main/resources/i18n/` 提供自己的 `messages*.properties`**（含业务 `tpl_*`/`org.fellow99.tpl` 键 + 需要的 RVP 键）。这正是父工程 `i18n/` 语料同步到 tpl-manage 的落点（§6.1、§7）。此点需在实现阶段以实际运行 `MessageUtils.message(...)` 验证确认。

## 五、父工程 i18n 总目录语料存储设计

### 5.1 设计目标与约束

1. **单一事实源**：所有多语言文案只在父工程 `i18n/` 维护一份，各端不重复维护。
2. **格式中立**：一套规范格式，可机械转换到各端原生格式（`.properties` / Vue TS / `strings.xml` / `string.json` / JSON）。
3. **符合宪法**：语料键命名对齐 `specs/constitution.md` 原则 3（模块 camelCase）、原则 4（模块编号跨端对齐）；**不 fork RVP 源码**（原则 1）。
4. **可校验**：能做 key 一致性、缺译、未用键检查。

### 5.2 规范语料格式（Canonical Format）

**推荐：扁平点号 key 的 JSON**（如 `"auth.loginFailed": "用户名或密码错误"`）。

选型理由（对比嵌套 JSON / `.properties` / TS 模块）：

| 候选 | 优点 | 缺点 |
|------|------|------|
| **扁平点号 JSON（推荐）** | 各语言可解析；与 `.properties` 一一对应；与 Android/Harmony 资源名只需 `.`→`_` 转换；vue-i18n 原生支持 `$t('a.b.c')`；diff 友好 | 需一次「打平/展开」工具函数（轻量） |
| 嵌套 JSON | Vue 生态最自然 | 与 `.properties`/Android 资源名需展开，跨端转换成本高 |
| `.properties` 作为源 | Java 原生 | JS/Android/Harmony 解析不便，且无标准注释/结构 |
| TS 模块作为源 | 前端直接 import | 后端与原生端无法消费 |

因此：**扁平点号 JSON 为唯一事实源**，各端原生格式由生成脚本产出（§7.2）。

### 5.3 目录结构

```
i18n/
├── README.md                 # 语料规范、命名约定、贡献/同步说明
├── common/                   # 跨端共享语料（通用按钮/错误码/提示）
│   ├── zh-CN.json            # 扁平点号 key
│   └── en-US.json
├── app/                      # 用户端语料（tpl-app-api 返回的 key + 各用户端 UI 文案）
│   ├── zh-CN.json
│   └── en-US.json
├── manage/                   # 管理端语料（tpl-manage 后端 + tpl-manage-ui 前端）
│   ├── zh-CN.json
│   └── en-US.json
└── scripts/
    ├── sync-i18n.mjs         # 生成各端原生格式（核心同步脚本）
    └── verify-i18n.mjs       # key 一致性/缺译/未用键校验
```

**域划分说明**：

- `common/`：跨端共享，如 `common.confirm`、`error.networkTimeout`（tpl-app-api 返回的错误 key 若跨端通用，也可放此处）。
- `manage/`：管理端专属（后端 properties 与前端 vue-i18n 共用同一份点号 key，生成脚本分别转成 `.properties` 与 TS）。

> 三域拆分避免单一巨型文件；`common` 供 app 端与管理端共同消费，`app`/`manage` 各自独立演进。

### 5.4 语料键命名规范

```
<模块域>.<场景>.<语义>
```

| 规则 | 说明 | 示例 |
|------|------|------|
| 分段 | 点号分隔；语义段 camelCase | `auth.loginFailed` |
| 错误码 | 统一 `error.<域>.<语义>` | `error.auth.loginFailed` |
| 占位符 | 统一 `{name}`（Java MessageFormat 与 vue-i18n 均兼容 `{0}`/`{name}`） | `auth.retryLimit: "重试超过 {0} 次"` |

各端转换时的字符适配（由 `sync-i18n.mjs` 处理）：

- Java `.properties`：点号 key 原样保留。
- Vue vue-i18n：点号 key 原样保留（`$t('auth.loginFailed')`），如需嵌套对象再展开。
- Android `strings.xml`：`.` → `_`（资源名不允许点号），如 `auth_login_failed`。
- HarmonyOS `string.json`：`.` → `_`，`name` 用转换后键。
- 小程序：JSON 点号 key 原样。

## 六、各子工程 i18n 落地方案

### 6.1 tpl-manage（后端，沿用 RVP 体系）

沿用 RVP 第一层「消息 i18n」，**不引入 key 返回模式**（管理端前端是 RVP-UI，走 `Content-Language` 头驱动的本地化）。

1. **补语料**：在 `tpl-manage-admin/src/main/resources/i18n/` 放置 `messages.properties` + `messages_zh_CN.properties` + `messages_en_US.properties`，由 `i18n/manage/*.json` 生成（含业务 `tpl_*`/自定义键，并按需并入用到的 RVP 键）。
2. **取词**：业务代码沿用 `MessageUtils.message("xxx")`（已随 ruoyi-common-core 依赖可用）。
3. **自定义异常/校验**：复用 `ValidatorConfig` 的 `{key}` 机制；业务键前缀 `tpl.` 或模块名。
5. **@Translation 引擎**：Spring Boot 4.1 下可直接沿用 `ruoyi-common-translation` + `ruoyi-common-json`，无需移植。

### 6.2 tpl-manage-ui（前端，沿用 RVP-UI 体系）

1. **继承上游**：继续通过 `@plus-ui` alias 继承 `RuoYi-Vue-Plus-UI/src/lang`（不修改上游，符合宪法原则 1）。
2. **品牌语料**：自定义文案落在本地 `tpl-manage-ui/src/lang/`，由 `i18n/manage/*.json` 生成 `zh_CN.ts` / `en_US.ts`，与上游键不冲突（本地 `tpl.*` 命名空间）。
3. **后端消息**：沿用 `Content-Language` 头方案（§3.5），`request.ts` 已具备，业务接口返回本地化字符串即可，无需改造。
4. **字典 label**：沿用 plus-ui 前端字典 i18n 做法。

### 6.3 tpl-app-api（后端，返回 key）

核心改造点——**面向前端的 message 一律返回 key**：

1. **统一响应**：`R.java` 的 `msg` 字段语义改为「i18n key」。成功/失败消息返回如 `"auth.registerSuccess"`、`"error.auth.loginFailed"`；仅日志/管理端内部文案保留真实文本。
2. **Key 契约**：定义 key 常量枚举（如 `MessageKey` 类），后端可返回的 key 是 `i18n/app/*.json`（及 `common`）中**真实存在**的键；`sync/verify` 脚本校验「后端返回的 key ⊆ 语料键集合」。
3. **带参消息**：key + `args` 数组，前端插值（如 `R.data.args` 或扩展 `msgArgs` 字段），避免后端拼串。
4. **后端自身 MessageSource**（可选）：为内部日志/审计做 i18n，可复用 §2.1 的 MessageUtils 方案（独立于「返回 key」契约）。
5. **兜底**：前端取不到 key 时回退显示 key 本身或英文兜底，保证不白屏。

> 说明：tpl-app-api 是独立工程（参考 RVP 但不依赖），MessageUtils 等需按需自建或轻量移植（仅 `spring.messages.basename` + 一个静态工具类即可）。

### 6.4 tpl-app-web（Vue 3 SPA）

1. 引入 vue-i18n（对齐 RVP-UI 版本 11.x，Composition 模式），新建 `src/lang/{index,zh_CN,en_US}.ts`，由 `i18n/app/*.json` + `i18n/common/*.json` 生成。
2. `appStore` 维护 `language` 状态 + `useStorage('language')` 持久化，`App.vue` 无需 `el-config-provider`（无 Element Plus），仅在挂载时 `i18n.global.locale` 联动。
3. **后端 key 翻译**：封装 `translateApiMessage(msg, args?)`，在 axios 拦截器统一对 `R.msg` 做 `$t(msg)`，命中返回译文、未命中回退原值；UI 文案直接 `$t('xxx')`。

### 6.5 tpl-app-android（Kotlin）

1. 采用 Android 原生资源限定符：新增 `res/values/strings.xml`（默认中文，已有）→ 保留，新增 `res/values-en/strings.xml`（英文）；后续可加 `values-zh-rCN/`。
2. 语料由 `i18n/app/*.json` + `i18n/common/*.json` 生成 `strings.xml`（key `.`→`_`）。
3. 运行时用 `context.getString(R.string.auth_login_failed, args...)`；语言切换依赖系统语言，或在 App 内做 `AppCompatDelegate.setApplicationLocales`（Android 13+）覆写。
4. **后端 key 翻译**：网络层拿到 `R.msg`（key）后，映射到 `R.string.*` 资源（维护 key→资源 id 映射，或直接用资源名约定 `error_auth_login_failed`），未命中回退原 key。

### 6.6 tpl-app-harmony（ArkTS）

1. 采用 HarmonyOS 原生资源限定：`resources/base/element/string.json`（默认）外，新增 `resources/zh_CN/element/string.json` 与 `resources/en_US/element/string.json`。
2. 语料由 JSON 生成 `string.json`（`{"name":"auth_login_failed","value":"..."}`）。
3. 运行时 `$r('app.string.auth_login_failed')`；语言跟随系统，或通过 i18n 能力（`i18n.System.getSystemLanguage()`）做应用内切换。
4. **后端 key 翻译**：`R.msg`（key）→ `$r('app.string.' + key.replaceAll('.','_'))`，未命中回退原 key。

### 6.7 tpl-app-mini（微信小程序）

1. 无成熟官方 i18n，采用**手写 locale 映射模块**：`miniprogram/i18n/{zh-CN,en-US}.ts`（点号 key 的扁平对象），由 `i18n/app/*.json` + `i18n/common/*.json` 生成。

4. **后端 key 翻译**：`R.msg` → `t(key)`，未命中回退原 key。
5. 语言偏好存 `wx.getStorageSync('language')`，默认跟随 `wx.getSystemInfoSync().language`。

## 七、语料同步方案（多方案对比）

语料从父工程 `i18n/`（事实源）同步到 7 个子工程，给出 4 个方案：

### 7.1 方案一：Git Submodule（语料仓库化）

把 `i18n/` 抽为独立 git 仓库 `tpl-i18n`，各子工程以 **git submodule** 引入到固定路径，构建期直接读取/转换。

- **优点**：单一事实源、版本可追溯可回滚、各端拿到同一份语料、可独立发版（语义化版本）。
- **缺点**：submodule 管理成本（每端 `update --init`、指针推进）；要求各端都接受「运行时读取 JSON」或「构建期转换」；子工程 CI 需处理 submodule 检出。
- **适用**：团队已习惯 submodule（本项目已用 9 个 submodule，工作流现成）。

### 7.2 方案二：构建期生成 + CI 分发（推荐）

父工程 `i18n/` 为唯一事实源，`scripts/sync-i18n.mjs` 把语料编译成各端原生格式，写入各子工程约定目录：

```
i18n/scripts/sync-i18n.mjs
  ├─ manage/*.json      → tpl-manage-admin/src/main/resources/i18n/messages*.properties
  ├─ manage/*.json      → tpl-manage-ui/src/lang/{zh_CN,en_US}.ts
  ├─ app/*.json+common  → tpl-app-web/src/lang/*.ts
  ├─ app/*.json+common  → tpl-app-android/app/src/main/res/values{,-en}/strings.xml
  ├─ app/*.json+common  → tpl-app-harmony/.../resources/{zh_CN,en_US}/element/string.json
  └─ app/*.json+common  → tpl-app-mini/miniprogram/i18n/*.ts
```

由父工程 CI（GitHub Actions）在语料变更时生成并提交到各子工程，或各子工程构建时从父工程语料生成（不提交生成物）。

- **优点**：格式转换灵活、各端拿到原生格式零适配、可集成 `verify-i18n.mjs` 做 key 一致性/缺译校验、无需 submodule 耦合、单脚本可控。
- **缺点**：需维护生成脚本；生成物若提交会形成重复；若不提交则构建期需访问语料源（可用「父工程产物 + 版本号」方式解耦）。
- **适用**：作为**主方案**。

### 7.3 方案三：运行期语料 API（后端下发）

tpl-app-api / tpl-manage 提供 `GET /api/i18n/{locale}` 返回语料 JSON，各前端启动/首屏拉取并缓存（localStorage/文件），后端语料更新后前端下次刷新生效。

- **优点**：热更新不发版、单一运行时来源、移动端可用（带离线内置兜底包）。
- **缺点**：首次加载需网络、离线/弱网兜底要处理、后端需维护语料版本号与缓存策略、增加接口与运维复杂度；与「语料随包」双轨易不同步。
- **适用**：作为**可选增强**（用户端线上热更新），不作为唯一来源。

### 7.4 方案四：Monorepo 符号链接 / Git Subtree（弱推荐）

各子工程用 pnpm workspace / git subtree / 符号链接直接共享 `i18n/`。

- **优点**：开发期改动即时可见。
- **缺点**：跨语言（Java/Kotlin/ArkTS）无法统一 workspace 工具链；subtree 合并冲突难维护；符号链接在 Android/Harmony 构建与 Windows 环境不稳定。
- **适用**：仅纯前端子集（web + manage-ui + mini）内部可局部采用，不覆盖全产品线。

### 7.5 方案对比与推荐

| 维度 | 方案一 Submodule | 方案二 生成+CI | 方案三 运行时 API | 方案四 链接/Subtree |
|------|:---:|:---:|:---:|:---:|
| 单一事实源 | ✅ | ✅ | ✅ | ⚠️ |
| 原生格式零适配 | ❌ 需各端转换 | ✅ 生成时转换 | ✅ JSON | ⚠️ |
| 热更新 | ❌ | ❌ | ✅ | ❌ |
| 离线可用 | ✅ 随包 | ✅ 随包 | ⚠️ 需兜底 | ✅ |
| 管理成本 | 中（submodule 指针） | 中（脚本+CI） | 高（接口+版本） | 高（冲突/跨语言） |
| 与现有工作流契合 | 高（已用 submodule） | 高 | 中 | 低 |

**推荐组合**：

1. **主方案 = 方案二**（构建期生成 + CI 分发）：父工程 `i18n/` 为事实源，`sync-i18n.mjs` 生成各端原生格式，`verify-i18n.mjs` 做校验，由父工程 CI 统一分发提交。
2. **承载方式 = 父工程 `i18n/` 直接入父仓库**（不必独立 submodule；若未来多产品线复用再抽 `tpl-i18n` 仓库 + 方案一）。
3. **可选增强 = 方案三**：用户端（web/android/harmony/mini）上线后如需要不发版更新语料，再叠加运行时语料 API，内置包做离线兜底。

## 八、实施建议与风险

### 8.1 建议实施顺序

1. 建立父工程 `i18n/`（规范 + `common`/`app`/`manage` 骨架 + 首批 key）。
2. 编写 `sync-i18n.mjs` + `verify-i18n.mjs`，先打通「manage 域 → tpl-manage-admin / tpl-manage-ui」的生成链路。
3. 改造 tpl-app-api 的 `R.msg` 为 key + 建立 `MessageKey` 契约。
4. 依次落地 tpl-app-web → android → harmony → mini 的 i18n 读取与后端 key 翻译。
5. 接入父工程 CI 自动分发 + 校验。

### 8.2 主要风险与对策

| 风险 | 说明 | 对策 |
|------|------|------|
| tpl-manage 语料 classpath 缺失 | RVP 语料在 ruoyi-admin，tpl-manage-admin 不依赖它 | §6.1 补齐 `tpl-manage-admin` 自身语料，运行验证 `MessageUtils` |
| 语料键漂移 | 后端返回 key 与前端语料不一致 | `verify-i18n.mjs` 校验「后端 key ⊆ 语料键」，CI 卡口 |
| 键命名字符差异 | Android/Harmony 资源名禁点号 | 生成脚本 `.`→`_` 统一转换 |
| 多语言语料膨胀 | 全量语料随包增大移动端体积 | 按端裁剪生成（app 端只打 app+common 域） |
| Jackson 版本差异 | RVP @Translation 引擎绑定 Jackson 3 | tpl-app-api 如需字段翻译，按目标 Jackson 版本移植 |
| 小程序 tabBar 不变量 | `app.json` 文案不可运行时 i18n | `wx.setTabBarItem`/`wx.setNavigationBarTitle` 切换时重写 |

### 8.3 待确认决策点

1. **语料事实源格式**：确认采用「扁平点号 JSON」（本文档推荐）。
2. **字典值多语言**：`tpl_*` 字典 label 是否需要后端多语言（RVP 未内置），还是前端 i18n 即可。
3. **是否独立语料仓库**：当前建议父工程 `i18n/` 直接入父仓库，多产品线复用再抽 `tpl-i18n`。
4. **运行时热更新**：用户端是否引入方案三（语料 API），MVP 阶段建议先随包、后评估。

## 附录三：语料 key 命名规范（统一命名空间）

重构后的语料 JSON 采用**单一命名空间**（不再区分多端），跨端相似语料已合并。key 规范：

| 前缀 | 含义 | 示例 |
|------|------|------|
| `message.*` | 信息反馈（成功/提示） | `message.registerSuccess`、`message.smsSent` |
| `message.error.*` | 错误/失败/校验反馈 | `message.error.loginFailed`、`message.error.phoneInvalid` |
| `auth.register.*` | 用户注册 UI | `auth.register.title`、`auth.register.submit` |
| `auth.login.*` | 用户登录 UI | `auth.login.tab.sms`、`auth.login.submit` |
| `auth.wechat.*` | 微信登录 | `auth.wechat.login` |
| `auth.profile.*` | 个人中心 | `auth.profile.editInfo`、`auth.profile.logout` |
| `ui.*` | 布局 / 导航 / 菜单 | `ui.nav.back`、`ui.nav.drawerOpen` |
| `<业务英文名>.*` | 业务功能 | `profile.title`、`profile.empty.title` |
