## 一、核实结论（现状）

### 1.1 一句话结论

当前 tpl-app-api 的用户注册（`POST /auth/register`）与用户登录（`POST /auth/login`）所提交的用户名、密码是 **明文传输** 的：

1. **应用层**：请求体（JSON）中的 `password` 字段无任何加密，后端直接按明文反序列化后交给 BCrypt；
2. **传输层**：部署侧 Nginx 仅监听 80 端口，**未配置 HTTPS/TLS**，即链路本身也是明文。

因此密码在「各端（浏览器 / Android / 鸿蒙 / 小程序）→ Nginx → tpl-app-api」全链路均可被中间人/抓包工具直接读取。

### 1.2 证据（代码级核实）

**后端（tpl-app-api）**

| 文件 | 关键代码 | 结论 |
|------|----------|------|
| `controller/AuthController.java` | `register(@RequestBody RegisterRequest req)` / `login(@RequestBody LoginRequest req)` | 直接反序列化明文 JSON，无任何解密过滤器/拦截器 |
| `model/dto/LoginRequest.java` | `private String password;` | 密码是普通字符串字段 |
| `model/dto/RegisterRequest.java` | `private String password;` | 同上 |
| `service/AuthService.java` | `BCrypt.hashpw(req.getPassword())`（注册）/ `BCrypt.checkpw(req.getPassword(), ...)`（登录） | 明文密码直达 BCrypt，证明请求体未解密 |
| `config/SaTokenConfigure.java` | 仅注册 `SaInterceptor`（登录校验），无解密 Filter | 无请求解密环节 |
| `pom.xml` | 依赖仅 Sa-Token / MyBatis-Plus / PostgreSQL / Lombok / Hutool / commons-pool2 | 未引入任何 AES/RSA 加密组件 |

**前端（tpl-app-web）**

| 文件 | 关键代码 | 结论 |
|------|----------|------|
| `api/index.ts` | 请求拦截器仅注入 `Authorization` 头 | 无 `isEncrypt` / `encrypt-key` 头，无加密逻辑 |
| `api/auth.ts` | `service.post('/auth/login', data)` / `service.post('/auth/register', data)` | 密码明文提交 |
| `views/LoginPage.vue` | `password: form.password` | 明文提交 |
| `views/RegisterPage.vue` | `password: form.password` | 明文提交 |
| `package.json` | 依赖仅 axios / vue / pinia / vue-router / lucide | 无 `crypto-js`、无 `jsencrypt` |

**其他端（tpl-app-android / tpl-app-harmony / tpl-app-mini）——同为明文**

| 端 | 文件 | 关键代码 | 结论 |
|----|------|----------|------|
| Android | `data/remote/RetrofitClient.kt` / `AuthApi.kt` | 仅 `AuthInterceptor`（token），无加密拦截器 | 明文提交 |
| 鸿蒙 | `service/ApiClient.ets` | 注释明确「当前未实现 AES+RSA，采用明文 JSON 传输」 | 明文提交 |
| 小程序 | `utils/crypto.ts` / `utils/request.ts` | `ENCRYPT_ENABLED=false`，`encryptRequest` 为透传占位 | 明文提交（已预留加密骨架） |

**部署层**

| 文件 | 关键代码 | 结论 |
|------|----------|------|
| `deploy/nginx/nginx.conf` | `listen 80;` 且无 `listen 443 ssl` / `ssl_certificate` | 无 TLS 终止，无 HTTPS |

## 二、风险分析

| # | 风险 | 严重度 | 说明 |
|---|------|:--:|------|
| R1 | 密码明文在链路中暴露 | **高** | HTTP 明文 + 无应用层加密，抓包即得密码 |
| R2 | 重放攻击 | 中 | 即便后续加密，若加密报文可被整体重放，仍可伪造登录请求 |
| R4 | 弱 JWT 密钥（既存问题） | 高 | `sa-token.jwt-secret-key: abcdefghijklmnopqrstuvwxyz`（tpl-app-api README I-001 已记录），即使传输加密，token 本身仍可被伪造 |
| R5 | 前端 JS 的「透明性」错觉 | 低 | 前端公钥加密本身不防「恶意中间人替换公钥」，真正的机密性依赖 HTTPS |

> 关键认知：**应用层加密（AES+RSA）解决的是「HTTP 明文链路下的点对点机密性」，HTTPS/TLS 解决的是「传输层机密性 + 身份认证 + 防篡改」。二者是互补而非替代**。若不上 HTTPS，仅靠前端 RSA 公钥加密，仍存在「中间人替换公钥」的中间人攻击面；若只上 HTTPS 而不做应用层加密，在带日志脱敏不完善、内网旁路抓包、以及「HTTPS 卸载后到后端之间的内网明文」等场景下仍有暴露。最佳实践是 **两者都做**。

## 三、加密方案设计

### 3.1 为什么「纯 RSA 公钥加密」不可行 / 不可取

用户提到「引入 public-key 加密机制」。直接对密码字段做纯 RSA 公钥加密存在以下问题：

2. **性能差**：RSA 加解密比对称加密慢数个数量级，不适合加密稍大的数据。
3. **无法复用对称加密的灵活性**。

因此业界标准做法（也是 RuoYi-Vue-Plus 的做法、TLS 自身的做法）是 **混合加密**：

```
RSA（非对称）负责保护一把「一次性随机 AES 密钥」
AES（对称）  负责加密真正的请求体
```

即：**「AES 加密 body + RSA 加密 AES key」**。RSA 只需加密 16/24/32 字节的 AES 密钥，规避了长度与性能问题，同时获得公钥加密的前向安全收益。

### 3.2 推荐方案：AES + RSA 混合加密（与 RuoYi-Vue-Plus 对齐）

**核心思想**：每次请求生成一把全新的随机 AES 密钥，用服务端 RSA 公钥加密该 AES 密钥后放入请求头，用该 AES 密钥加密请求体。服务端用 RSA 私钥解密出 AES 密钥，再用其解密请求体，还原明文 JSON 后走原有 `@RequestBody` 反序列化。

```
┌─────────────┐                                        ┌─────────────┐
│  tpl-app-web  │                                        │  tpl-app-api │
│  (浏览器)     │                                        │ (SpringBoot)│
└──────┬──────┘                                        └──────┬──────┘
       │ 1. 生成随机 AES Key (aesKey, 16/24/32 字节)            │
       │ 2. body = AES_encrypt(JSON, aesKey)                  │
       │ 3. header["encrypt-key"] = RSA_encrypt(Base64(aesKey))│
       │                                                       │
       │   POST /auth/login                                    │
       │   Header: encrypt-key: <RSA密文>                       │
       │   Body: <AES密文(Base64)>                              │
       │──────────────────────────────────────────────────────▶│
       │                                                       │ 4. RSA_privkey 解密 header → Base64(aesKey)
       │                                                       │ 5. Base64 解码 → aesKey
       │                                                       │ 6. AES 解密 body → 明文 JSON
       │                                                       │ 7. 反序列化 → LoginRequest（明文密码）
       │                                                       │ 8. BCrypt.checkpw(...)
       │◀───────────────────────────────────────────────────────│
```

### 3.3 算法与参数选择

| 项 | RuoYi-Vue-Plus 现状 | 本方案建议 | 说明 |
|----|---------------------|-----------|------|
| 对称算法 | AES（ECB + PKCS7） | AES（**GCM 优先**，CBC 次之；ECB 仅作兼容兜底） | ECB 模式不隐藏数据模式，属已知弱点；GCM 自带完整性校验（AEAD），强烈推荐 |
| 对称密钥 | 随机 32 字节（前端 `crypto.getRandomValues`） | 同左，每次请求重新生成 | 一次性密钥，用完即弃 |
| 非对称算法 | RSA PKCS#1 v1.5 | RSA（**OAEP 优先**，PKCS#1 v1.5 兼容兜底） | OAEP 抗选择密文攻击更优 |
| RSA 密钥长度 | ≥ 1024（框架最低校验） | **2048 位**（生产推荐） | 1024 位已被认为不安全 |
| 密钥生命周期 | 前端构建时内置公钥 | 见 §3.4 | 建议支持轮换 |

> 说明：为与 RuoYi 样本保持实现一致性、降低落地成本，首版可先按 RuoYi 的「AES-ECB + RSA PKCS#1 v1.5」实现（tpl-app-api 已内置 Hutool，后端零新增依赖），并将算法模式抽象为可配置，后续平滑升级到 GCM/OAEP。因为每次请求都换随机 AES 密钥，ECB 的「重复块」弱点被大幅缓解。

### 3.4 密钥管理与公钥下发

RSA 公私钥对是加密机制的核心资产，需明确管理策略：

| 决策点 | 选项 | 建议 |
|--------|------|------|
| 密钥生成 | 离线工具生成（`openssl genrsa` / Hutool `generateRsaKey()`） | 一次性生成，私钥永不进入代码仓库 |
| 私钥存储（后端） | 环境变量 / 配置中心 / KMS / 挂载 Secret | **环境变量或挂载 Secret**，禁止硬编码（当前 JWT 弱密钥问题同源） |
| 公钥下发（前端） | ① 构建时注入（`VITE_APP_RSA_PUBLIC_KEY`）② 后端提供 `GET /auth/public-key` 动态下发 ③ 硬编码常量 | **① 或 ②**。动态下发（②）便于密钥轮换但多一次请求；MVP 建议 ① 构建时注入 |
| 密钥轮换 | 支持双公钥过渡 | 建议预留 `kid`（密钥版本号）字段，便于灰度轮换 |

**后端建议新增配置项**（命名对齐 RuoYi）：

```yaml
# application.yml 新增
api-decrypt:
  enabled: true                # 加解密总开关（dev 可关闭以便调试）
  header-flag: encrypt-key     # 携带 RSA 加密 AES 密钥的请求头名
  private-key: ${RSA_PRIVATE_KEY}   # 服务端 RSA 私钥（Base64 PKCS#8），来自环境变量
  # public-key: ...            # 若响应也加密才需要；本方案仅请求加密，可不配
```

### 3.5 后端设计（示意，非实现）

在 `tpl-app-api` 中新增一个「请求解密过滤器」，放在 `SaInterceptor` 之前执行，仅对带 `encrypt-key` 头的 POST/PUT 请求生效。因 tpl-app-api 已依赖 `hutool-all`，可直接使用 `cn.hutool.crypto.SecureUtil`（`SecureUtil.aes` / `SecureUtil.rsa`），**无需新增后端依赖**。

```
新增文件（示意）
├── config/
│   └── ApiDecryptProperties.java     # @ConfigurationProperties(prefix="api-decrypt")
├── filter/
│   ├── ApiDecryptFilter.java          # 判定是否需要解密、异常处理（可复用/参考 RuoYi CryptoFilter）
│   └── DecryptRequestBodyWrapper.java # 包装 request，解密 body（参考 RuoYi DecryptRequestBodyWrapper）
└── util/
    └── EncryptUtils.java              # AES/RSA 加解密工具（参考 RuoYi EncryptUtils）

改造点（示意）
├── config/SaTokenConfigure.java       # 注册解密 Filter（在 SaInterceptor 之前）
├── config/CorsConfig.java             # 确认 CORS 放行自定义头 encrypt-key
```

解密核心逻辑（伪代码，与 RuoYi 对齐）：

```
if (method in [POST, PUT] && header[encrypt-key] 非空):
    aesKeyBase64 = RSA.decrypt(header[encrypt-key], privateKey)   # 1. RSA 私钥解出 Base64(AES key)
    aesKey       = Base64.decode(aesKeyBase64)                     # 2. Base64 解码
    plainBody    = AES.decrypt(rawBody, aesKey)                    # 3. AES 解出明文 JSON
    request 替换为带 plainBody 的 wrapper（可重复读）
```

**改造范围（最小侵入）**：`AuthController` / `AuthService` / DTO / Mapper **完全不动**——解密在过滤器层完成，控制器仍按原样接收明文 `LoginRequest` / `RegisterRequest`。

### 3.6 端侧设计（四端，示意，非实现）

加密机制需在 **web / android / harmony / mini** 四个端侧一致落地。各端遵循**同一份 wire 协议契约**（见 3.6.1），仅实现方式因技术栈而异。

#### 3.6.1 跨端统一契约（wire 协议，四端 + 后端必须严格一致）

这是各端与后端 `ApiDecryptFilter` 之间唯一的兼容性契约，任何一端实现偏差都会导致解密失败：

| 环节 | 约定 | 说明 |
|------|------|------|
| 对称算法 | AES-256，ECB 模式，PKCS#7 填充 | MVP 对齐 RuoYi；升级 GCM 需四端+后端同步切换 |
| AES 密钥 | 32 字节（由 32 字符随机 hex 字符串的 UTF-8 字节构成） | 与 RuoYi `generateRandomString()` 一致，规避「随机字节非合法 UTF-8 导致后端 Base64→String 失真」问题 |
| 非对称算法 | RSA-2048，PKCS#1 v1.5 | 仅用于加密 AES 密钥 |
| 密钥传输 | `header["encrypt-key"] = RSA_pub(Base64(aesKey_utf8_bytes))` | AES key 先 Base64，再 RSA 公钥加密 |
| 请求体 | `body = Base64(AES_encrypt(JSON字符串, aesKey))` | 整个 JSON 字符串加密后 Base64 |
| 触发标识 | 请求头 `isEncrypt: true` | 仅注册 / 登录 / 改密标注；各端发送后需移除该头 |

> **关键点（跨语言兼容）**：AES 密钥必须按**原始字节**使用（`SecretKeySpec(rawBytes)` / cryptoFramework SymKey / CryptoJS WordArray 直作密钥），**不得经过 passphrase-KDF 派生**。RuoYi 前端用 `CryptoJS.enc.Utf8.parse(hexString)` 得到 WordArray 直作密钥，Java 侧 Hutool `SecureUtil.aes(keyBytes)` 亦按原始字节——四端必须保持这一「原始字节」语义，否则跨语言解密结果不一致。

#### 3.6.2 tpl-app-web（Vue 3）

`tpl-app-web` 需新增两个轻量依赖（与 RuoYi-Plus-UI 一致）：

| 依赖 | 用途 |
|------|------|
| `crypto-js` | AES 加解密 |
| `jsencrypt` | RSA 公钥加密 |

```
新增文件（示意）
├── src/utils/
│   ├── crypto.ts        # generateAesKey / encryptBase64 / encryptWithAes（对齐 plus-ui crypto.ts）
│   └── jsencrypt.ts     # encrypt()：JSEncrypt + VITE_APP_RSA_PUBLIC_KEY（对齐 plus-ui jsencrypt.ts）

改造点（示意）
├── src/api/index.ts     # 请求拦截器：当 isEncrypt=true 且 method∈{post,put} 时，
│                        #   aesKey=generateAesKey()
│                        #   headers['encrypt-key']=encrypt(encryptBase64(aesKey))
│                        #   data=encryptWithAes(JSON.stringify(data), aesKey)
├── src/api/auth.ts      # loginApi/registerApi 请求头加 { isEncrypt: true }
└── .env / .env.production# VITE_APP_RSA_PUBLIC_KEY=...
```

拦截器伪代码（对齐 plus-ui `request.ts`）：

```
if (config.headers?.isEncrypt && ['post','put'].includes(method)):
    aesKey = generateAesKey()                          // 32 字节随机
    config.headers['encrypt-key'] = encrypt(encryptBase64(aesKey))  // RSA(公钥)加密 Base64(AES key)
    config.data = encryptWithAes(JSON.stringify(config.data), aesKey)
```

> 也可选**原生 Web Crypto API**（`crypto.subtle` 的 RSA-OAEP + AES-GCM）替代 `crypto-js`+`jsencrypt`，零依赖、安全性更高，但实现稍复杂。MVP 建议先用 `crypto-js`+`jsencrypt` 快速对齐 RuoYi，后续可升级。

#### 3.6.3 tpl-app-android（Kotlin）

**技术栈**：Retrofit 2 + OkHttp 4 + Gson；加密走 Android 内置 JCE（`javax.crypto` / `java.security`），**零新增依赖**。

| 能力 | 实现 |
|------|------|
| AES | `Cipher.getInstance("AES/ECB/PKCS5Padding")` + `SecretKeySpec(keyBytes, "AES")`（16 字节块下 PKCS5 == PKCS7） |
| RSA | `Cipher.getInstance("RSA/ECB/PKCS1Padding")` + `KeyFactory.getInstance("RSA")` 解析 X.509 公钥 |
| 随机密钥 | `SecureRandom` 生成 32 字符 hex 字符串 |
| Base64 | `android.util.Base64`（`NO_WRAP`） |
| 公钥来源 | `buildConfigField("RSA_PUBLIC_KEY", ...)` 构建时注入（与 `API_BASE_URL` 同法，见 `app/build.gradle.kts`） |

**集成点**：新增 `EncryptInterceptor`（OkHttp `Interceptor`），在 Retrofit 完成 Gson 序列化之后、真正发包之前对 body 加密：

```
新增/改造（示意）
├── data/remote/EncryptInterceptor.kt  # 新增：拦截 POST/PUT，加密 body + 写 encrypt-key 头
├── data/remote/RetrofitClient.kt      # 改造：.addInterceptor(EncryptInterceptor(...))，置于 AuthInterceptor 之后
├── data/remote/AuthApi.kt             # 改造：register/login 加 @Headers("isEncrypt: true")
└── util/CryptoUtils.kt                # 新增：AES/RSA 工具（对齐 RuoYi EncryptUtils）
```

拦截器逻辑（伪代码）：

```
if (method in [POST, PUT] && header["isEncrypt"] == "true"):
    aesKey = randomHex(32)                                      # 32 字符 hex
    body   = AES_ECB_PKCS7_encrypt(原始JSON, aesKey.utf8Bytes)  # 读取并 buffer 请求体
    header["encrypt-key"] = RSA_PKCS1_encrypt(Base64(aesKey.utf8Bytes), publicKey)
    header 移除 "isEncrypt"
    用加密后的 body 重建 RequestBody，chain.proceed()
```

> 注意：① OkHttp 拦截器读取 body 后需用 `RequestBody` 重建（`buffer()` 或可重复读包装）；② 密文 body 的 `Content-Type` 与 web 端保持一致；③ 加密拦截器置于 `AuthInterceptor` 之后、`HttpLoggingInterceptor` 之前，避免日志泄露明文。

#### 3.6.4 tpl-app-harmony（ArkTS）

**技术栈**：`@kit.NetworkKit`（`@ohos.net.http`）；加密走鸿蒙原生 `@kit.CryptoArchitectureKit`（`@ohos.security.cryptoFramework`），本工程 API 19~23 完全支持，**零新增依赖**。

| 能力 | 实现 |
|------|------|
| AES | `cryptoFramework.createCipher('AES256|ECB|PKCS7')` + `createSymKeyGenerator('AES256').convertKey({data})` |
| RSA | `cryptoFramework.createCipher('RSA2048|PKCS1')` + `createAsyKeyGenerator('RSA2048').convertKey(pubKeyBlob, null)` |
| 随机密钥 | `cryptoFramework.createRandom().generateRandomSync(32)` → 转 hex 字符串 |
| Base64 | `@ohos.util` 的 `util.Base64Helper` |
| 公钥来源 | `BuildProfile.RSA_PUBLIC_KEY`（与 `API_BASE_URL` 同法，`build-profile.json5` 注入） |

**集成点**：改造 `ApiClient.ets` 的 `request()`，对 POST/PUT 且带 `isEncrypt` 标记的请求加密 body + 写 `encrypt-key` 头：

```
新增/改造（示意）
├── service/ApiClient.ets        # 改造：request() 内接入加密（新增可选 isEncrypt 参数）
├── service/AuthService.ets      # 改造：login/register 传 isEncrypt=true
├── utils/CryptoUtil.ets         # 新增：cryptoFramework 封装（AES/RSA/随机 hex）
└── constants/ApiConstants.ets   # 新增 HEADER_ENCRYPT_KEY / HEADER_IS_ENCRYPT
```

> 注意：① cryptoFramework 为**异步 API**（`createCipher` / `convertKey` / `doFinal` 均返回 Promise），需在 `request()` 中 `await`；② RSA 公钥导入需 X.509 格式 `DataBlob`（Base64 解码后包 `{data}`）；③ `ApiClient` 目前是静态方法 + 单一 `request()`，改造点集中、侵入面小。

#### 3.6.5 tpl-app-mini（微信小程序）

**技术栈**：`wx.request`（已封装 `utils/request.ts`）；小程序**无 Web Crypto API**，需引入 JS 加密库或微信原生能力。

| 能力 | 实现 |
|------|------|
| AES | `crypto-js`（纯 JS，小程序环境可直接运行） |
| RSA | 方案 A：`jsencrypt`（需补 `window`/`navigator` polyfill，或改用小程序适配的 RSA 实现）；方案 B：微信原生 `wx.getUserCryptoManager()`（基础库 ≥ 2.21.0，仅提供 `getRandomValues`，RSA 仍依赖 JS 库） |
| 随机密钥 | `wx.getRandomValues`（基础库 ≥ 2.21.0，真随机）或 `crypto-js` 内置伪随机 |
| 公钥来源 | 构建期注入常量 / 后端动态下发（`GET /auth/public-key`）——**见待决策 D3** |

**现状**：`utils/crypto.ts` 已预留加密骨架（`ENCRYPT_ENABLED=false` + `encryptRequest()` 透传），`utils/request.ts` 已接入 `ENCRYPT_ENABLED` 分支并预留 header 注入。落地时只需实现 `crypto.ts` 真实加密并置 `ENCRYPT_ENABLED=true`。

```
新增/改造（示意）
├── utils/crypto.ts    # 改造：实现 generateAesKey / encryptWithAes / rsaEncrypt（替换透传占位）
├── utils/request.ts   # 已就绪：ENCRYPT_ENABLED 分支已接好，无需大改
└── config.ts          # 新增：RSA_PUBLIC_KEY 常量（或改走动态下发）
```

> 注意：① 现有占位注释写的是「AES-CBC + 请求头 `encryptKey`」，与本契约（**AES-ECB + 头 `encrypt-key`**）**不一致，落地时需纠正**；② `jsencrypt` 依赖 `window`/`navigator`，小程序需 polyfill 或换用轻量纯 TS 的 RSA 公钥加密实现；③ 小程序主包体积受限（≤ 2MB），RSA 库选择需兼顾体积。

### 3.7 响应是否加密

本方案**仅对请求（登录/注册上行）做加密**，响应（token 等）不加密，理由：

1. 上行是密码等敏感信息，下行 `access_token` 本身已通过 Sa-Token 签发，且走 HTTPS 即可；
2. RuoYi 的 `ApiEncrypt.response()` 响应加密为可选能力，MVP 阶段不必要。

如后续对敏感接口的响应也要加密，可复用同一套 RSA/AES 工具，反向对称实现。

### 3.8 加密范围边界（白名单制，已定）

**结论：仅「含密码」的接口加密，不是全站加密。**

#### 3.8.1 机制：按接口 opt-in（白名单）

加密由各端请求头 `isEncrypt: true` 逐接口触发（见 §3.6.1），后端过滤器据此解密。因此「哪些接口加密」是一个**白名单**，由各端显式标注，而非全局强制。

#### 3.8.2 MVP 白名单（已定）

| 接口 | 方法/路径 | 加密 | 依据 |
|------|-----------|:--:|------|
| 用户注册 | `POST /auth/register` | ✅ | 含 `password` |
| 用户登录 | `POST /auth/login` | ✅ | 含 `password` |
| 修改密码 | `PUT /system/user/password` | ✅ | 含 `password`（`oldPassword` / `newPassword`） |
| 验证码 | `GET /auth/code` | ❌ | 无敏感字段（验证码 5 分钟失效） |
| 登出 | `POST /auth/logout` | ❌ | 无 body |

#### 3.8.3 不加密的内容（边界）

1. **登录后接口**：携带 `Authorization` token，已由 token + HTTPS 双重保护，不叠加应用层加密；
2. **GET 查询参数**：加密只作用于请求体（POST/PUT body），GET 的 query 不在范围；
3. **响应**：MVP 不加密响应（见 §3.7）。

#### 3.8.4 扩展路径（无需推倒重来）

将来某接口出现敏感字段，只需在该端加 `isEncrypt: true` 标记即可单独纳入白名单。但若扩展至**全站加密**，需额外解决两个问题：

1. **GET 请求**：查询参数不在 body，需另定加密方案（加密 query / 改 POST）；
2. **响应加密**：需后端增加「响应加密」能力（§3.7），工作量翻倍。

## 四、实施路径（分阶段）

> 本报告仅设计，以下为实现时的建议顺序，供后续落地参考。

### 阶段 0：HTTPS（最高优先级，先于应用层加密）

1. 为域名申请 TLS 证书，Nginx 增加 `listen 443 ssl` + `ssl_certificate` + HTTP 强制跳转 HTTPS；
2. 确认 `/auth/**`、`/api/**` 均被 HTTPS 覆盖。

### 阶段 1：后端解密过滤器

1. 新增 `api-decrypt` 配置项（`application.yml` + 环境变量注入私钥）；
2. 新增 `EncryptUtils`（复用 Hutool，AES/RSA）；
3. 新增 `ApiDecryptFilter` + `DecryptRequestBodyWrapper`；
4. 在 `SaTokenConfigure` 注册 Filter，确认 CORS 放行 `encrypt-key` 头；
5. 单测：用「RSA 公钥加密 AES key + AES 加密 body」构造请求，断言能正常登录/注册。

### 阶段 2：四端加密

按 §3.6 的 wire 契约，四端并行落地（后端过滤器就绪后各端可独立联调）：

1. **web**：安装 `crypto-js`、`jsencrypt`；新增 `utils/crypto.ts` / `utils/jsencrypt.ts`（公钥走 `VITE_APP_RSA_PUBLIC_KEY`）；`api/index.ts` 拦截器接入；`api/auth.ts` 标注 `isEncrypt: true`。
2. **android**：新增 `EncryptInterceptor` + `util/CryptoUtils.kt`（JCE）；`RetrofitClient` 注册拦截器；`AuthApi` 的 register/login 标注 `@Headers("isEncrypt: true")`；公钥走 `buildConfigField("RSA_PUBLIC_KEY")`。
3. **harmony**：新增 `utils/CryptoUtil.ets`（cryptoFramework）；`ApiClient.request()` 接入；`AuthService` login/register 传 `isEncrypt=true`；公钥走 `BuildProfile.RSA_PUBLIC_KEY`。
4. **mini**：实现 `utils/crypto.ts`（crypto-js + RSA），置 `ENCRYPT_ENABLED=true`；`utils/request.ts` 分支已就绪；公钥走常量或动态下发。
5. **端到端验证**：四端分别用「RSA 公钥加密 AES key + AES 加密 body」构造请求，断言后端正常解密、`password` 在抓包中不可见。

### 阶段 3：加固与收尾

1. JWT 密钥改为环境变量强随机（修复既有 I-001）；
2. 增加防重放：请求头附 `timestamp` + `nonce`（与加密报文绑定，服务端校验时间窗 + 一次性 nonce），或复用验证码 `uuid` 的一次性消费机制作为天然防重放；
3. 算法模式升级（AES-GCM + RSA-OAEP）与密钥轮换（`kid` 版本号）；
4. 四端协议一致性回归：用同一组固定样本（明文 JSON + 固定 AES key + 固定公钥）在四端生成密文，断言与后端 Hutool 解密结果一致（锁定 §3.6.1 契约）。

## 五、安全加固建议（必读）

1. **HTTPS 是地基**：应用层加密不能替代 TLS，二者必须叠加。中间人替换公钥的风险只能靠 HTTPS 的证书校验消除。
2. **私钥绝不出服务端、不入前端、不入仓库**：前端只有公钥；RSA 私钥通过环境变量/Secret 注入，与 JWT 密钥同一治理标准。
3. **一次性密钥 + 防重放**：每次请求随机 AES 密钥；结合 `timestamp + nonce`（或验证码 `uuid` 一次性消费）防重放。
4. **算法选安全模式**：AES 避免 ECB、RSA 避免裸 PKCS#1 v1.5，优先 GCM + OAEP；至少 2048 位。
5. **保留开关与灰度**：`api-decrypt.enabled` 开关 + 双公钥过渡，便于灰度与回滚。
6. **验证码链路联动**：加密应覆盖「验证码 + uuid」字段，避免只加密密码而验证码明文导致的重放窗口。

4. **仅**以下三个接口的**请求体**允许出现 `password` 字段，且该字段内容必须**加密传输**（AES+RSA 混合加密，见本文档 §三）：

## 八、结论

1. **现状**：tpl-app-api 注册/登录的用户名、密码当前为**明文传输**，且部署层无 HTTPS——设计文档 `002` 中标注的「AES+RSA 加密」尚未在代码落地。
2. **方案**：推荐 **AES + RSA 混合加密**（RSA 保护一次性 AES 密钥、AES 加密请求体），与 RuoYi-Vue-Plus 完全对齐；后端复用 Hutool（零新增依赖），四端按技术栈各自实现（web= `crypto-js`+`jsencrypt`；android/harmony= 内置 JCE / cryptoFramework 零依赖；mini= `crypto-js`+RSA 库），统一遵循 §3.6.1 的 wire 契约。
3. **原则**：**HTTPS 优先、应用层加密叠加**；私钥安全治理与 JWT 弱密钥问题一并修复；算法选安全模式并预留开关与轮换能力。
