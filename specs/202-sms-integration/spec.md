# 短信平台 API 对接 功能规格

> 模块：202-sms-integration
> 状态：已设计（实现中）
> 设计文档：`../docs/202-短信平台API对接.md`
> 更新日期：2026-08-14

---

## 1. 模块概述

### 1.1 目的

tpl-workspace 用户侧（tpl-app-api）在注册、登录、找回密码等场景需要向用户手机发送**短信验证码**。本模块对接第三方短信平台 **Spug Push**（https://push.spug.cc），实现短信验证码发送能力，并封装为可复用功能类供其他业务模块调用。

### 1.2 解决的问题

| 问题 | 说明 |
|------|------|
| 无短信通道 | 当前用户体系仅有图形验证码，缺少手机号验证码能力 |
| 自建短信成本高 | 无需自建短信网关、申请签名、等待模板审核 |
| 能力分散 | 短信发送逻辑封装为统一功能类，避免各模块重复对接 |

### 1.3 范围

**包含**：Spug Push `/sms/<TEMPLATE_CODE>` 接口对接、短信验证码发送功能封装、手机号-验证码缓存与消费机制、模板编码与超时等配置化。

**排除**：验证码生成与校验（由消费方业务模块负责）、发送状态查询、发送记录查询、短信签名申请、IP 白名单管理（均通过 Spug 控制台完成）。

---

## 2. 用户故事

- 作为开发者，我可以调用统一封装类向指定手机号发送短信验证码，无需关心 HTTP 细节。
- 作为用户（间接），我在注册/登录时能收到手机短信验证码。
- 作为运维，我可以通过配置文件切换短信模板编码与超时参数。

---

## 3. 功能需求

### 3.1 短信验证码发送

- **FR-202-001**：系统 MUST 提供短信验证码发送功能封装类，供其他业务模块调用。
- **FR-202-002**：系统 MUST 通过 `POST https://push.spug.cc/sms/<TEMPLATE_CODE>` 调用短信接口。
- **FR-202-003**：请求体 MUST 为 JSON，字段为 `to`（接收手机号，必填）与 `code`（验证码，必填）。
- **FR-202-004**：`TEMPLATE_CODE` MUST 通过配置文件（application.yml）注入，MUST NOT 硬编码在代码中。
- **FR-202-005**：系统 MUST 校验手机号格式（11 位，以 1 开头），非法时拒绝发送。
- **FR-202-006**：系统 MUST 校验验证码格式（4-6 位数字或字母），非法时拒绝发送。
- **FR-202-007**：系统 MUST 解析响应中的 `code`、`msg`、`request_id` 字段并返回给调用方。
- **FR-202-008**：响应 `code == 200` 表示发送成功，其余值表示失败。
- **FR-202-009**：系统 SHOULD 支持配置连接超时与读取超时。

### 3.2 配置化

- **FR-202-010**：短信平台基础地址 MUST 可配置（`sms.base-url`），默认 `https://push.spug.cc`。
- **FR-202-011**：模板编码 MUST 可配置（`sms.template-code`）。

### 3.3 验证码缓存与消费

- **FR-202-012**：系统 MUST 为一个手机号仅缓存一个验证码（Redis Key 按手机号唯一）。
- **FR-202-013**：手机号-验证码缓存 MUST 10 分钟失效（Redis TTL）。
- **FR-202-014**：发送验证码时，若手机号已缓存验证码且未过期，MUST NOT 变更验证码、MUST NOT 重复发送。
- **FR-202-015**：发送验证码时，若手机号未缓存验证码或已过期，MUST 生成新验证码、缓存并触发短信平台发送。
- **FR-202-016**：系统 MUST 提供验证码消费方法，入参为手机号与输入验证码。
- **FR-202-017**：消费时，若手机号+输入验证码与缓存一致，MUST 清空该手机号-验证码缓存并返回 true；否则 MUST 返回 false。

## 4. 关键实体

| 实体 | 说明 |
|------|------|
| SmsSendResult | 发送结果：`code`（200 成功）、`msg`、`requestId`（用于查询发送状态） |
| SmsProperties | 短信配置：base-url、template-code、连接/读取超时 |
| 验证码缓存 | Redis，Key `sms_code:{手机号}`，TTL 10 分钟 |

## 5. 验收场景

### 场景：正常发送验证码

- Given 传入合法手机号（11 位）与合法验证码（4-6 位）
- When 调用短信发送封装类
- Then 向 Spug Push 发起 POST 请求，返回 `code=200` 与 `request_id`

### 场景：手机号非法

- Given 传入非法手机号
- When 调用短信发送封装类
- Then 抛出参数异常，不发起 HTTP 请求

### 场景：验证码非法

- Given 传入非法验证码（长度/字符不符）
- When 调用短信发送封装类
- Then 抛出参数异常，不发起 HTTP 请求

### 场景：上游返回失败

- Given 短信平台返回业务失败（如额度不足、模板变量错误）
- When 调用短信发送封装类
- Then 返回非 200 的 `code` 与失败原因 `msg`

### 场景：验证码缓存去重

- Given 某手机号已缓存验证码且未过期
- When 再次调用发送
- Then 不重新生成验证码、不重复发送短信

### 场景：验证码消费成功

- Given 手机号+输入验证码与缓存一致
- When 调用消费方法
- Then 清空该手机号-验证码缓存，返回 true

### 场景：验证码消费失败

- Given 手机号+输入验证码与缓存不一致（或缓存不存在）
- When 调用消费方法
- Then 返回 false

---

## 6. 非功能需求

- 发送调用 MUST 设置超时（连接超时 5s、读取超时 10s），避免上游不可达时无限阻塞。
- 模板编码 MUST 仅存在于服务端配置，MUST NOT 出现在网页或移动端安装包中。
- 发送失败 SHOULD 记录日志，便于排查。

---

## 7. 约束与假设

- MVP 仅实现验证码发送，发送状态查询、发送记录等后续接入。
- 模板内容为 Spug 平台官方模板（`您的验证码是${code}，十分钟内有效...`），不可修改。
- 短信发送必须由业务服务端发起。

---

## 8. 依赖

- 上游：用户认证（002）、找回密码等业务模块——短信验证码的消费方。
- 下游：Spug Push 短信平台（https://push.spug.cc）。
